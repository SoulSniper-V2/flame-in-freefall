1.0           SCOPE

1.1           Identification
The purpose of this document is to identify the design of the communication interfaces used by
the Advanced Combustion via Microgravity Experiments (ACME).

1.2           System Overview

The Advanced Combustion via Microgravity Experiments (ACME) is mini-facility designed to
support Principal Investigators (PI) interested in studying various aspects of advanced
combustion in a microgravity environment. ACME will be integrated into the Fluids and
Combustion Facility’s (FCF) Combustion Integrated Rack (CIR) onboard the International Space
Station in the US Lab Module.
ACME will perform microgravity experiments to study fire suppression/flame extinguishment
via 5 experiments: s-flame, Flame design, CLD Flame, E-Field Flames, and Burning Rate
Emulator Flames as described in the ACME Baseline Description Document, ACME-DOC-004.
ACME will allow investigation using pure as well as mixtures of gaseous fuels at various
chamber atmosphere pressures, compositions, and oxygen concentrations. The microgravity
environment allows for observation and measurement of flame formation and extinguishment
processes that cannot be made in sustained gravity. The modular design of ACME allows for
flexibility in configuration for specific experiments and easy maintainability of the hardware.
The core elements of gaseous combustion are included in the ACME design as a basis for current
and future gaseous combustion studies. These elements are establishment of gas flow through
various exchangeable mass flow controllers, ignition of gas at the burner and the use of
appropriate diagnostic measurement devices. The five identified experiments, and any future
experiments, use these core elements to build a unique set of requirements for the study of
various phenomena distinctive to gaseous combustion. The goal of ACME is to improve the
fundamental understanding of combustion processes in order to enable increased efficiency and
reduce pollutant emission in practical combustion.


1.3           Document Overview
This document is divided into interfaces used to communicate with the ISS (i.e., external
communication interfaces) and interfaces used to communicate with devices within ACME that
require a protocol (i.e., internal communication interfaces).

3.0              EXTERNAL COMMUNICATION INTERFACES

3.1              CIR Input/Output Processor (IOP) Interface
Commands sent through the CIR IOP (Input Output Processor) are in the format required by
FCF-ICD-0076A. See section A.1, FCF Command Protocol for a listing of the required
command formats, including all required headers. All commands from the ground go to the IOP
with the FCF Command Header and User Data filled in. Commands from ACME to the IPSUs
and IPSU-Gs go through the FCFCommunications application (Base Classes) which fills in the
Command Sequence Count and Time Fields in the FCF Command Header before submitting the
packet to the IOP for routing.

3.1.2         ACME Common Group Command Details
These commands are called ‘common’ because they are implemented using code shared
between several payloads. The detailed descriptions below are derived from the original
documentation for these commands in Appendix K of FCF-ICD-0076, Rev C or later. As stated
in that appendix the high order bytes of the command ID are replaced by the command group
number assigned to ACME common commands, which is 0xC0. In that appendix the command
IDs range from 0x0001 to 0x0038. For ACME they range from 0xC001 to 0xC038.
3.1.2.1       NullCommand
The NullCommand does nothing. It can be used to test communication paths.

Command ID: 0xC001
Mnemonic: ACME_COMMON_NULL
3.1.2.2       ExternalCommand
The ExternalCommand command allows an avionics Main Processor (MP) CSCI to have no
knowledge of this command and make use of the External Module feature. The command is
passed to an External Module without intervention. This command enforces the requirement that
an External Module requires a “module identifier” as the first parameter. The command group
portion of the command ID, XX, depends on the module.

Command ID: 0xXX02
Mnemonic: ACME_COMMON_EXTERNAL_PASS_THRU

                               # Bytes
           Parameter                                          Description
                                Type
                                  2
    moduleIdentifier                     Identifier (e.g. camera number 1,2)
                               Uint16
    Command parameters           80      Area for module command-dependent parameters.

3.1.4.38       IntensifiedCameraSafe
The IntensifiedCameraSafe command places the intensified camera in a state that is safe for
turning on lights without harming the camera by sending commands to the IPSUG. The filter is

3.1.7.11        PmtSetGain
The PmtSetGain command sets the gain of the specified photo multipler tube.

The gain parameter in this command specifies the volts out of the cube DNx-AO-333 board
channels AO-25, AO-26, and AO-27, see Table 18. These voltages are fed through a voltage
divider of 10 Kohms and 1.21 Kohms before entering the control input on the PMT. According
to the PMT data sheet the recommended control voltage is 0.5 V to 1.1 V, corresponding to 4.63
V to 10.19 V for the gain command parameter, which is limited to a maximum of 10 V.

The equation to convert PMT control input, x, to PMT gain is:
                            PMTGain = 2,000,000 * x ^ 8.643856
,which gives a range of PMTGain from 5000 to 3,500,000 for 0.5 V to 1.1V control input, or
4.63 V to 10.19 V command gain parameter.

The equation to convert command gain parameter, gain, to PMT gain is:
              PMTGain = 2,000,000 * (gain/9.2645) ^ 8.643856

The equation to convert PMT gain to command gain parameter, gain, is:
              gain = 10 ^ (0.115689 * log(PMTGain) + 0.23786213)

7.2            AcmeLogging.ini
This file located in /payload/app/config allows filter levels to be configured so that more or less
information shows up in the telemetry and file message logs. In the message log each message
contains a logging category, for example “acme.diag” or “zt.fcf”. To turn off a category make a
rule in AcmeLogging.ini. For example, “acme.diag=false” turns off any message with the
acme.diag category. Comments in the file indicate available categories.

7.3            Motion_ACME.ini
This file located in /payload/app/config contains configuration for motion control of the camera
package when ACME is controlling the camera motion instead of IPSU-G. It specifies the
camera serial port (serialPortNumber=3 means use /dev/ttyS3) and parameters for each axis.
While no longer used it may still be included to show what IPSU-G should have for this file.

7.4            Script Files
Script files are used to conduct automated operations using the commands: SetScriptDirectory,
LoadScript, RunScript, AbortScript, PauseScript, ResumeScript, and ChangeScriptParameter.
They are named with a .js extension (for java script) and are typically stored in the
/payload/app/scripts/ directory or any sub-directory of /payload/app/scripts, but can be anywhere
as long as the SetScriptDirectory and/or LoadScript commands specify the location.
The language used to write script files is technically ECMAScript-262 ( http://www.ecma-
international.org/publications/files/ECMA-ST/Ecma-262.pdf). A brief summary can be
currently found at https://wiki.qt.io/JavaScript.
Many ACME functions and variables have been made visible to the scripts. All commands and
their parameters can be used. All current telemetry is available. Public methods in controllers
derived from XSystemController can be called. Any other objects passed to the QT macro
Q_DECLARE_METATYPE(object) in the ACME source code can be used.
Several helper functions are preloaded to the script engine and can also be used. print(message)
logs a message. sendCommand(command) sends the specified command to the command
handler. uSleep(time) pauses script execution for the specified number of milliseconds.
More helper functions are loaded from the script file “/payload/app/scripts/helpers.js” if it exists.
Here is an example of a basic ACME script:
       // BasicScript.js

       // When RunScript command is received this says to execute the run function below
       AcmeAvionicsController.runScript.connect(run);

       //This variable must be named parameters so the ground and flight software can manipulate the
       values.
       var parameters = { parameter1:1.0, parameter2:4, parameter3:true };

       // from helpers.js. This tells the ground software the parameters and values so they can be
       // displayed and modified using the ChangeScriptParameter command
       printParams();

8.0            OUTPUT FILES

8.1            Data Output File
Data output files are created using the SystemOpenTestPoint command which creates a file
named and stored at /payload/sci/testpointName_x/testpointName_x_data.csv, where
testpointName is the parameter received in the SystemOpenTestPoint command and _x is
optional to avoid duplicate files, where x = 1,2,3, etc.
The file contains a two-line header. The first line has the date and time, documentation of the
setup received in a SystemDefineSetup command, and the PMT gains. The second line has the
column headings for the subsequent rows of data. The text of the column headings is defined by
the Diagnostics/Header registry entry or the Diagnostics/BreHeader entry depending on whether
the SystemDefineSetup command experimentType parameter was BRE or not. The column
headings should match the data which is the following:
        - A timestamp in the format HH:MM:SS:mmm, where mmm is milliseconds.
        - 11 channels of analog input from the cube DNx-AI-207 board in the order shown in
            Table 16.
        - 25 channels of analog input from the cube DNx-AI-225 board in the order shown in
            Table 17. (The names of many of these values change depending on whether it is a
            BRE test or not, hence the two options for header.)
        - Channel AO-4 of the DNx-AO-333 analog output board. This is the E-Field control
            voltage.
Rows of comma-separated data is added to the file between DataRecordingStart and
DataRecordingStop commands at a rate defined by the Diagnostics/SampleTimeMsec registry
entry, see Table 32, defaulting to 8 msec for 125 Hz sampling.

8.2            Mass Flow Controller Setpoint File
If the registry value Flow/WriteMfcSetpointsToFile is true when the SystemOpenTestPoint
command is executed then a file of MFC setpoints is created alongside the data output file. The
name of the file will be /payload/sci/testpointName_x/testpointName_x_mfcSetpoints.csv. The
first row of text contains the same header as the data output file. The second row contains the
headers, “Time,MFCA1Setpoint(V),MFCA2Setpoint(V),MFCA3Setpoint(V)”. Subsequent
rows are written whenever one of the three MFCs change setpoints and includes the changed
setpoint and the current setpoints of the other two MFCs, and a timestamp with millisecond
resolution. The file is close when the SystemCloseTestPoint command is executed.

8.3            Message Log File
Software messages are logged to files named and stored at /payload/logs/YYYY-MM-DD_hh-
mmACME.log, where YYYY is year, MM is month, DD is day of month, hh is hour, and mm is
minutes. The date in the name is when the log file is created, soon after software startup.
Each message line in the file begins with a timestamp and a logging category. The timestamp is
of the format YYYY-MM-DD DDD hh:mm:ss:mmm, where DDD is day of the year, mmm is
milliseconds, and the rest are self-explanatory. See section 1.1 for information about the logging
category and how to filter them out if desired.

                                                                                 ACME-DOC-010 Rev D


8.4            Command Log File
The message log file, section 8.3, includes messages showing commands received and their
parameters. Command log files contain only the details of each command received. The files
are named and stored at /payload/logs/YYYY-MM-DD_hh-mmACMECommands.log. The
format is for each command received a timestamped line of text with the command name
followed by timestamped lines of text showing each parameter name and parameter value,
including header information.

1.0     INTRODUCTION

The Smoke Aerosol Measurement Experiment (SAME) instrument is an experiment payload planned for
the Microgravity Science Glovebox (MSG) located on the International Space Station (ISS). Throughout
this document the term “project” is used to refer to the SAME project in its role as payload developer.

1.1     Purpose

The purpose of this Software Description Document is three-fold:
   (1) to describe the Software Management Plan (SMP) for the project
   (2) to identify what product specification and procedure documentation will be produced as part of the
   software effort for the project, and
   (3) to identify and describe the records that will be produced as part of the software effort.
This document is intended to be used as a roadmap of the software development effort, describing some
aspects of the road within the document itself and, as applicable, pointing to other software documents
and records which will be completed as the project progresses.
The basis for this document, including structure, are two Glenn Research Center (GRC) Manuals, GRC-
P2.6.4 and GRC-M2.6.4. Refer to these documents for more detailed background information and
terminology definitions.

1.2     Scope

This Software Description Document establishes the project's management processes for the software to
be developed by the project to satisfy its requirements. It also contains requirements to be satisfied by the
providers of all software purchased, contractually acquired, developed, or maintained for the support or
execution of the project. And except for software and hardware interfaces used to estimate capabilities
and schedules for the availability of support resources, it does not apply to software applications that
provide company-wide capabilities not specific to this project.
The term "software" as used in this document includes code, documentation, associated data, and
"firmware", which is software installed in a medium that cannot be dynamically changed.
The project software is comprised of several software “packages”, each executing on a separate platform.
Located within the MSG will be a microcontroller-based data acquisition and control unit (DACU) that is
responsible for direct control of the experiment. Connected to this controller is the MSG Laptop
Computer (MLC) which will contain software to provide a crew interface into the DACU. Ground
support software will be developed to collect and analyze on-orbit data at the GRC Telescience Support
Center (TSC). Test software may be developed to assist in the development and testing of hardware
subsystems. This document is applicable to all of these packages. Any specific exceptions will be
identified in the appropriate section.

2.2        Development Activities Plan

The Development Activities Plan describes the path and standards to follow in getting from concept to
finished product.

2.2.1      Lifecycle Approach

The project will follow the conventional GRC Basic Software Lifecycle as shown below:

      Requirements
                                Design          Development        System Testing      Release              Support
   User     Software



                                         Figure 1 - Basic Software Lifecycle

The following is a summary of the software tasks, deliverables, and processes performed during each Life
Cycle phase.
Requirements: Document requirements. Perform any agreed upon inspections and/or reviews.
Acceptance Test Plan is started at this time.
Design: Develop the design; document the design. Perform any rapid prototyping, and then capture the
results in the design documentation. Write software system-level test plans and procedures. Perform
agreed upon inspections and reviews.



                                                              4
                                                                                  SAME-DOC-003 Rev A


Development: Implement the design, i.e., code the software. Devise and perform unit-level testing.
Perform any agreed upon inspections or walk-throughs. Finalize and release integration and software
system-level test procedures. Perform informal regression testing as features are added.
System Testing: Perform software system-level testing, record errors, and fix problems. Document
changes to the design, to the requirements, and to the code.
Release: Perform any agreed upon customer demonstrations/tests. Record and store the version of the
release. Finalize, review and sign-off on any user documents. Get customer agreement on delivery—a
release authorization. For High and Critical Control Level, a version description document is required. It
is highly recommended for Medium control software efforts as well. This project will supply a version
description document.
Support: Provide agreed upon level of version support to customers. Record and address any problems.
Review requests for added features. Determine the need for updates and follow this procedure for any
additional development. (Updates to the flight software are not possible for this project, but changes to
ground support software and others are not unlikely). Provide operation assistance to users of the
software.

2.2.2   Schedule

The software development schedule is closely tied to the project schedule. See SAME-PLN-001, Project
Plan. Following are software development tasks and milestones described in relation to the project
milestones and phases.

2.2.2.1 SCR/RDR Phase

During this project phase the software requirements document and supporting software interface control
document will be drafted. The software management plan and the software assurance plan will be created
and approved.

2.2.2.2 PDR Phase

During this project phase the software requirements document and software interface control document
will be finalized and approved. The software design document will be started with emphasis on the
architectural design. Development hardware and software will be acquired and assembled into the
development system. The design document will be completed and signed off after a software design
review in time for the PDR itself. Preliminary test plans will be written and reviewed. Coding of software
will begin with emphasis on supporting individual sub-systems of the functional model which is to be
completed by PDR. Functional model software will be baselined.

2.2.2.3 CDR Phase

During this project phase the flight, crew, and ground software will continue to be developed with testing
of sub-systems as hardware is available. The software acceptance test will be created, approved, and run
on completed software with a complete system. Flight and ground software is baselined and a Software
Readiness Review is conducted. Approval of the crew display by NASA’s Payload Display Review
Team, including a usability test, will be acquired. Integrated testing with MSG, as required, will be
performed. The operations manual will be written. Software will support the mission sequence test and
respond to scientist requests for changes as necessary. Final loading of software, release and validation
will be performed in time for the Verification Readiness Review (VRR).

2.2.2.4 Post Pre-ship Review

During this period ground software and tools supporting ground operations and data processing can be
created or enhanced. The Operations Manual will also be enhanced.

2.2.2.5 Mission Operations

During mission operations the software team will support operations, trouble-shooting, and further create

2.2.2.6 Post Mission Operations

After the mission is over, downlinked data will be safely stored. Data storage media brought back from
the ISS, if any, will be backed up and data will be retrieved, compared to downlinked data, and safely

2.2.3   Release Process

A project software release is a complete package of every software module created that is necessary to
operate the onboard payload system, payload crew display, payload ground control system, or any test
support software (see SAME-PLN-008, Ground Support Equipment Plan). A software release is under
version control and configuration management in such a way that the project can say for certain that the
software that is being used is the software that was tested. If necessary, a past or present configuration
can be reproduced using the records generated during a software release and the files stored in the
software repository or configuration management system.
Refer to SAME-PLN-002, Configuration Management Plan, for software release requirements.

2.2.4   Simulations

Where possible and as available, ISS program simulators provided to the project will be utilized. As
required for validation and assurance, the project may develop its own software and/or hardware
simulators. An MSG software simulator has already been developed by ZIN and will be used in place of
MSG during development and testing.

2.2.5.1 Hardware

Project software will be developed on an x86 computer running Windows XP or better using the tools
listed below. Compiled embedded control software and the operating system image for the DACU will
be transferred to the DACU CPU’s data storage over a private ethernet network. The DACU CPU is an
x86 single board computer located on a PC/104 electronics board. The DACU can be run by resetting or
re-powering or, in debug mode, by initiating payload software from the development computer. An
RS422 interface between the development computer and DACU CPU simulates and tests the
communication link between the payload and MSG.

2.2.5.2 Operating Systems

Embedded control software for the DACU will be developed to run under the QNX Real-Time Operating
System (RTOS) by QNX Software Systems Ltd. (The QNX RTOS is also known as Neutrino.) It is a
scalable, POSIX compliant, deterministic, and multi-threaded operating system.
Custom project software for the MSG Laptop Computer will be developed to run under Windows NT 4.0,
or as directed by MSG (an upgrade is possible in the near future).
Custom project software for ground control at the TSC will be developed to run under Windows XP and
will use the Telescience Research Kit (TreK) from MSFC to communicate with ISS command and data
interfaces.

Wherever possible the project will use C++ as the programming language.

The project will use 60081-STD-0066, BXF Software Coding Standard, to provide coding guidelines to

All project software, including low control level software, will be placed under version control. Version

version control database will be automatically archived using the existing ZIN network backup system.
Version control will be achieved using Subversion by tigris.org.

2.3     Verification and Validation Plan

Verification addresses whatever steps a project is going to use to assure that the requirements are
completely and correctly incorporated in the software product. Validation states how the project intends
to get confirmation that what is being designed, built, and delivered meets those requirements.
The project will perform verification by inspection. SAME-DOC-006, Software Design Document, will
provide traceability to each specific requirement in SAME-DOC-004, Software Requirements Document.
Verification will be completed prior to source code implementation and will involve a design review as
specified in SAME-PLN-006, Software Assurance Plan.
The project will perform validation by testing. SAME-TST-001, Software Acceptance Test, will be
developed and executed to ensure that the software performs as expected. In addition to nominal
operations, this test will validate appropriate reaction, as defined by the software requirements, to off-
nominal and boundary conditions. A mission sequence test will be developed and executed at the project
level to ensure validation of the entire system, hardware and software. The crew display will be
additionally validated by a usability test at Johnson Space Center (JSC). Integrated testing of the
experiment with MSG will be performed as well, as required by MSFC-RQMT-2888, MSG Investigation
Interface Requirements Document. Prior to, and in-between releases of software, informal module testing
will be performed to ensure functionality of each module.

Risk management is addressed at the project level through SAME-PLN-001, Project Plan. However,
procedure P04003, Design Control Procedure for Software, of QM001, ZIN Technologies Quality
Manual requires that the software risk level be assessed, and that will be done here.
Following the guidelines of P04003 it is determined that the software risk for the project is Medium. A
medium level of risk is characterized as “In-use software failure risks significant property damage or
significant negative impact upon the customer”. The influencing point in this decision is the fact that
samples are destroyed in testing and therefore science data losses during the test cannot be recovered by
re-running the sample test. There is not a risk of significant property damage, only of negative impact
upon the customer.

3.0     PRODUCT SPECIFICATION

There are number of software-related product specification documents recommended by GRC-P2.6.4.
The manner in which these are implemented by the project are listed below.

3.1     Concept Documentation

Not required for medium control level software.           Refer to SAME-DOC-001, Concept Description
Document, for the project-level concept.

3.2     Requirements Documentation

The project will develop SAME-DOC-004, Software Requirements Document, which will contain all
software requirements pertaining to systems, facility, safety, operations, telemetry, software interfaces,
functionality and performance. This document will also contain any limitations or constraints on the
system and will specify the required responses to off-nominal and boundary conditions.

3.3     Design Documentation

The project will develop SAME-DOC-006, Software Design Document, which will contain both the
architectural software design and the detailed software design. It is expected that these sections will be
added at separate times.
The architectural design will lay out the basic structure for the software defining the high level interfaces
between software and hardware and any other systems as well as define the domains, objects, modules,
functions and operations needed to meet the requirements. Operational scenarios and use cases will be
documented as part of the design to assure the design covers all the aspects of operation. Timing diagrams
and flow charts will be used to convey the architecture and the real-time command and data flow.
Network diagrams may be used to describe the physical and data interactions on the network in the final
installation.
The detailed software design will specify details that are worked within and between the modules, classes,
and/or objects. For Object Oriented Design (OOD), the public versus private sectors will be determined.
Parameter and variable types and values will be established. Global versus private flags, variables, and
parameters will be determined. Methods, attributes, calculations, and algorithms will be captured.

011, Flight Software Version Description Document, respectively. VDDs are not required for test support
software. The VDD will indicate compatability with other package versions. For example, “This version
of ground software will work with versions 1.0–2.5 of flight software.” Additional requirements for the
VDD are listed in SAME-PLN-002, Configuration Management Plan. It is suggested that the VDD
contain the sections shown below.

4.0     PROCEDURES

See the Validation and Software Assurance Plan in previous sections for the use of procedures by the
project. This section describes the content of the procedures.

4.1     Testing Procedures

The project will develop SAME-TST-001, Software Acceptance Test, which will perform all internal
validation tasks on released software. This procedure will contain a requirements matrix which will
indicate the source of each requirement and the step(s) in the procedure in which it is tested. The
procedure will clearly delineate pass/fail criteria for each test within the procedure. The results of the
procedure will be documented in a report numbered according to SAME-PLN-002, Configuration
Management Plan.
The mission sequence test procedure for full instrument validation for the PI is specified at the project
level.
Any integrated testing with MSG will follow procedures developed by MSG with input from the project.
Procedures for usability testing of the crew display software will be developed by JSC personnel with
input from the project.

5.0     RECORDS

This section describes how the recommended software records listed in Table 2 are implemented and
handled in this project. Most of these records are a result of following subsections of the software
management plan, Section 2.0.

5.1     Project Approval/Work Authorization

A record of approval/work authorization for the software effort of the project is part of the record for the
entire project. Refer to the project level document, SAME-PLN-001, Project Plan.

5.2     Design Review Records

During software design reviews, with occurrence as dictated by SAME-PLN-006, Software Assurance
Plan, minutes will be taken and a summary report will be generated that is signed off by all design review
members. At this point SAME-DOC-006, Software Design Document, will be modified to either
reference a document containing the summary report or the report content itself will be appended to
SAME-DOC-006. In addition, for each review a memo describing the results of the review will be sent to
the GRC Project Manager.
Minutes from other software meetings will be stored and backed-up electronically.

5.3     Review or Board Records

Record of project level reviews and board response, for example the Verification Readiness Review and
the Pre-Ship Review, are kept at the project level according to SAME-PLN-001, Project Plan.

5.4     Problem Reports / Corrective Action Reports

As specified in SAME-PLN-006, Software Assurance Plan, the project will record and track to closure
any problems found in software using procedures P13001, Procedure for The Control of Nonconforming
Product, and P14001, Corrective and Preventive Action Procedure, of QM001, ZIN Technologies Quality
Manual. The project shall use the non-conformance tracking and corrective action reporting as described
in the Quality Manual once the software has passed software acceptance testing.

5.5     Verification and Validation Results

Verification results consist of the record from the software design review. See Section 5.2 for more
information.
Internal validation results for the project software releases will be in the form of a signed Software
Acceptance Test Report. Results of the validation accomplished by the mission sequence test will be
generated at the project level according to SAME-PLN-003, Product Assurance Plan.
External validation results, such as from the crew display usability test and any integrated MSG testing
may exist as a memo or e-mail, in which case the text of the results will be stored electronically in a
backed-up folder.

5.6     Design Change Documentation

Requests for changes to the software design and the software itself will be maintained in an electronic log
by the lead software engineer. This log will include the date and origin of the request, description of the
request, and the disposition: incomplete, in process, completed with date, or cancelled with date. The log
will be stored in a backed-up folder.
A record of design changes will also be kept in the version control database in the form of comments
entered at the time that source code changes are checked in or when COTS packages are updated or
replaced.

5.7     Release Authorization

A memo or e-mail from the Project Lead/Lead Engineer or Project Manager is required to authorize the
release of a new software version. This may be in the context of the Software Lead announcing the
upcoming release by e-mail and the Project Lead/Lead Engineer or Project Manager responding in
approval.
